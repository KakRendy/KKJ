Fokus pembelajaran bukan hanya menghafal nama algoritma. Mahasiswa perlu memahami apa yang hendak dilindungi, mekanisme apa yang digunakan, dan bagaimana perlindungan tersebut dapat diverifikasi.

Bab I

Fundamental Concepts of Cryptography

Memahami pengertian, tujuan, istilah, dan model dasar kriptografi sebagai fondasi untuk mempelajari algoritma dan protokol keamanan.

1.1 Pengertian Kriptografi

Kriptografi merupakan bidang ilmu yang mempelajari teknik untuk melindungi informasi dengan memanfaatkan konsep matematika, algoritma, dan kunci. Secara historis, kriptografi berkaitan dengan penulisan pesan tersembunyi. Dalam sistem komputer modern, fungsinya jauh lebih luas: menjaga kerahasiaan, mendeteksi perubahan, mengautentikasi pihak atau pesan, dan mendukung pembuktian asal suatu dokumen.

Kriptografi digunakan ketika pengguna membuka website melalui HTTPS, mengakses server melalui SSH, melakukan transaksi perbankan, menandatangani dokumen elektronik, atau menyimpan data terenkripsi. Mekanisme dipilih sesuai kebutuhan. Enkripsi digunakan ketika isi data perlu dirahasiakan; hash atau MAC digunakan untuk mendeteksi perubahan; tanda tangan digital digunakan untuk memverifikasi pesan atau dokumen.

Perkembangan kriptografi dapat dipahami melalui tiga tahap umum. Pertama, classical cryptography yang banyak menggunakan substitusi dan transposisi karakter, misalnya Caesar cipher. Kedua, kriptografi modern yang memanfaatkan algoritma matematis dan komputer, seperti DES dan AES. Ketiga, kriptografi kunci publik dan protokol modern yang memungkinkan pertukaran kunci, tanda tangan digital, sertifikat, dan komunikasi aman melalui jaringan terbuka.

Cryptography

Merancang, menganalisis, dan menggunakan mekanisme untuk melindungi informasi.

Cryptanalysis

Menganalisis kelemahan atau mencoba memperoleh informasi dari sistem kriptografi tanpa mengetahui rahasia yang semestinya.

Keduanya saling melengkapi. Perancang perlu memahami bagaimana mekanisme dapat diserang, sedangkan analis keamanan perlu memahami prinsip kerja algoritma agar dapat menemukan kesalahan implementasi atau konfigurasi.

Prinsip Kerckhoffs

Prinsip Kerckhoffs menyatakan bahwa keamanan sistem kriptografi seharusnya tetap bertahan meskipun cara kerja algoritmanya diketahui pihak lain. Rahasia utama berada pada kunci, bukan pada penyembunyian algoritma. Prinsip ini menjadi dasar penggunaan algoritma terbuka yang dapat ditinjau dan diuji komunitas keamanan.

1.2 Tujuan dan Layanan Keamanan Kriptografi

Kriptografi mendukung beberapa layanan keamanan. Layanan tersebut saling berhubungan, tetapi tidak identik. Satu mekanisme dapat memberikan lebih dari satu layanan, sedangkan beberapa kebutuhan memerlukan kombinasi mekanisme.

Confidentiality (Kerahasiaan)

Confidentiality memastikan isi informasi hanya dapat dibaca pihak yang memiliki otorisasi. Enkripsi mengubah plaintext menjadi ciphertext sehingga pihak yang tidak memiliki kunci sesuai tidak dapat membaca isi pesan secara langsung. Contohnya enkripsi data transaksi ketika dikirim melalui HTTPS atau enkripsi file yang tersimpan pada perangkat.

Integrity (Integritas)

Integrity berkaitan dengan kemampuan mendeteksi perubahan data yang tidak diharapkan, baik penyisipan, penghapusan, maupun penggantian isi. Hash dapat digunakan untuk membandingkan sidik jari digital data, sedangkan MAC atau authenticated encryption memberikan perlindungan integritas yang terikat pada kunci.

Authentication (Autentikasi)

Authentication adalah proses memverifikasi identitas pihak atau keaslian sumber pesan. Dalam komunikasi web, browser memeriksa sertifikat dan bukti kriptografi untuk memverifikasi server. Dalam komunikasi berbasis HMAC, penerima memeriksa apakah pesan dibuat oleh pihak yang memiliki secret bersama. Dalam digital signature, penerima memverifikasi signature menggunakan public key yang dipercaya.

Non-repudiation (Nirpenyangkalan)

Non-repudiation merupakan dukungan bukti agar pihak yang melakukan tindakan tertentu tidak dapat menyangkalnya secara mudah. Digital signature dapat mendukung tujuan ini karena signature dibuat menggunakan private key dan diverifikasi dengan public key. Namun, tanda tangan digital tidak otomatis menjadi bukti hukum mutlak. Keabsahannya bergantung pada pengaitan identitas dengan kunci, pengamanan private key, proses penerbitan sertifikat, pencatatan waktu, kebijakan, dan aturan hukum yang berlaku.

Batasan penting

Enkripsi tidak otomatis mencegah penghapusan data oleh pengguna yang memiliki hak akses. Hash biasa tidak membuktikan siapa pengirimnya. Digital signature tidak menyembunyikan isi dokumen. Mekanisme harus dipilih sesuai layanan keamanan yang dibutuhkan.

1.4 Perbedaan Mekanisme Pengolahan Data

Encoding, encryption, hashing, MAC, dan digital signature sering terlihat menghasilkan keluaran berupa karakter acak atau string panjang. Kemiripan tampilan tersebut tidak berarti fungsinya sama.

Encoding dan Decoding

Encoding mengubah representasi data ke format tertentu agar mudah disimpan atau dipertukarkan. Base64, hexadecimal, dan URL encoding merupakan contoh encoding. Encoding tidak dirancang untuk merahasiakan informasi. Siapa pun yang mengetahui formatnya dapat melakukan decoding tanpa secret key.

Plaintext:  keamanan
Base64:     a2VhbWFuYW4=
Decoding:   keamanan

Jika kredensial hanya diubah ke Base64, kredensial tetap dapat dibaca setelah decoding. Karena itu, Base64 bukan pengganti enkripsi.

Encryption dan Decryption

Encryption dirancang untuk menjaga kerahasiaan. Prosesnya menggunakan algoritma dan kunci. Pihak yang tidak memiliki kunci sesuai seharusnya tidak dapat memperoleh plaintext secara praktis. Keamanan enkripsi modern bergantung pada algoritma yang kuat, kunci yang memadai, dan penggunaan parameter yang benar.

Hashing

Hash function menerima input dengan panjang bervariasi dan menghasilkan digest berukuran tetap. Hash bukan cara menyembunyikan data dan tidak dirancang agar hasilnya dapat dibalik. Hash banyak digunakan untuk pemeriksaan integritas, identifikasi file, dan komponen protokol keamanan.

Message Authentication Code (MAC)

MAC dihitung dari pesan dan secret key bersama. Penerima yang memiliki secret yang sama dapat menghitung ulang nilai MAC dan membandingkannya. MAC memberikan perlindungan integritas serta autentikasi pesan di antara pihak-pihak yang berbagi secret.

Digital Signature

Digital signature dibuat menggunakan private key dan diverifikasi menggunakan public key yang sesuai. Signature mengikat pesan atau dokumen pada proses penandatanganan. Jika pesan berubah, verifikasi signature seharusnya gagal.

Bab II

Cryptographic Algorithms and Techniques

Mengenali kelompok algoritma kriptografi, cara kerja konseptual, karakteristik, dan batasan penggunaannya.

2.1 Symmetric Cryptography

Symmetric cryptography adalah kriptografi yang menggunakan satu secret key bersama untuk melakukan enkripsi dan dekripsi. Pengirim dan penerima harus memiliki kunci yang sama. Karena kunci tersebut menjadi rahasia bersama, distribusi, penyimpanan, dan pembatasan akses terhadap kunci merupakan bagian penting dari keamanan.

Misalnya, sebuah organisasi ingin mengirim file laporan keuangan kepada unit lain. File dapat dienkripsi menggunakan AES dengan secret key yang telah didistribusikan melalui mekanisme aman. Penerima menggunakan secret key yang sama untuk mendekripsi file. Jika pihak yang tidak berwenang memperoleh kunci, kerahasiaan file dapat terancam.

Block Cipher dan Stream Cipher

Block cipher memproses data dalam blok berukuran tetap. AES merupakan block cipher dengan ukuran blok 128 bit. Data yang lebih panjang ditangani menggunakan mode operasi. Stream cipher menghasilkan aliran keystream yang dikombinasikan dengan plaintext, umumnya menggunakan operasi XOR. Keduanya membutuhkan pengelolaan parameter dan kunci yang benar.

Advanced Encryption Standard (AES)

AES merupakan standar enkripsi simetris yang ditetapkan NIST. AES memproses blok 128 bit dan memiliki tiga pilihan panjang kunci, yaitu 128, 192, dan 256 bit. Nama AES-128, AES-192, dan AES-256 menunjukkan panjang kuncinya, bukan ukuran bloknya.

Secara garis besar, AES mengolah state melalui transformasi byte dan operasi linear. Putaran utama mencakup SubBytes, ShiftRows, MixColumns, dan AddRoundKey; putaran terakhir tidak menggunakan MixColumns. Kunci awal diperluas melalui proses key expansion untuk menghasilkan round keys.

Makna praktis AES

AES banyak digunakan untuk melindungi data karena efisien pada perangkat lunak maupun perangkat keras. Namun, penggunaan AES harus disertai mode operasi yang tepat, pengelolaan nonce/IV, serta autentikasi data jika mode yang dipilih tidak menyediakan autentikasi.

Mode Operasi AES

Mode operasi menentukan bagaimana block cipher digunakan untuk memproses data yang lebih panjang daripada satu blok. Mode yang berbeda memiliki karakteristik dan persyaratan keamanan yang berbeda pula.

ECB (Electronic Codebook) merupakan mode yang sebaiknya dihindari untuk data umum karena blok plaintext yang sama menghasilkan blok ciphertext yang sama di bawah kunci yang sama, sehingga pola data dapat terlihat. Dalam aplikasi modern, authenticated encryption seperti AES-GCM sering dipilih ketika sesuai dengan kebutuhan dan tersedia pada pustaka kriptografi tepercaya.

Kelebihan dan Keterbatasan Symmetric Encryption

Kelebihan

  • Efisien untuk volume data besar.
  • Relatif cepat dibanding operasi kunci publik.
  • Cocok untuk enkripsi file, disk, database, dan payload komunikasi.

Keterbatasan

  • Secret key harus dibagikan dengan aman.
  • Jumlah kunci meningkat ketika banyak pihak berkomunikasi.
  • Kebocoran secret key dapat membuka data yang dilindunginya.

2.2 Asymmetric Cryptography

Asymmetric cryptography atau kriptografi kunci publik menggunakan pasangan kunci yang memiliki hubungan matematis: public key dan private key. Public key dapat dibagikan kepada pihak lain. Private key harus dijaga oleh pemiliknya dan tidak boleh dibagikan.

Untuk skema enkripsi kunci publik, pengirim mengenkripsi data atau secret menggunakan public key penerima; penerima mendekripsi menggunakan private key miliknya. Untuk digital signature, prosesnya berbeda: pemilik menandatangani menggunakan private key, lalu pihak lain memverifikasi menggunakan public key.

Enkripsi kunci publik

Public key penerima digunakan untuk enkripsi; private key penerima digunakan untuk dekripsi.

Digital signature

Private key penandatangan digunakan untuk signing; public key digunakan untuk verification.

RSA

RSA merupakan algoritma kunci publik yang didasarkan pada operasi aritmetika modular dan kesulitan memfaktorkan bilangan komposit besar pada parameter yang dipilih dengan benar. Dalam penggunaan praktis, RSA tidak boleh digunakan sebagai operasi raw RSA tanpa skema padding. RSA-OAEP digunakan untuk enkripsi, sedangkan RSA-PSS merupakan skema tanda tangan yang direkomendasikan dalam banyak penerapan modern.

RSA dapat digunakan untuk enkripsi data berukuran terbatas atau, lebih umum, untuk melindungi kunci simetris yang kemudian digunakan mengenkripsi data utama. Operasi RSA relatif lebih berat daripada AES, sehingga tidak ideal untuk mengenkripsi seluruh data berukuran besar secara langsung.

Elliptic Curve Cryptography (ECC)

ECC adalah keluarga teknik kriptografi yang memanfaatkan struktur matematis kurva eliptik pada medan berhingga. ECC bukan satu algoritma tunggal. Beberapa mekanisme yang termasuk keluarga ini adalah ECDH untuk key agreement, ECDSA untuk tanda tangan digital, dan EdDSA untuk tanda tangan digital berbasis kurva Edwards.

ECC dapat memberikan tingkat keamanan tertentu dengan ukuran parameter yang lebih kecil dibandingkan RSA untuk tingkat keamanan yang sebanding. Hal ini dapat menguntungkan pada perangkat dengan sumber daya terbatas. Namun, pemilihan kurva, implementasi, dan parameter tetap harus mengikuti standar serta pustaka tepercaya.

Key Exchange dan Key Agreement

Key exchange atau key agreement memungkinkan dua pihak memperoleh secret bersama tanpa mengirim secret tersebut secara langsung melalui jaringan. Diffie-Hellman dan ECDH merupakan contoh mekanisme yang digunakan untuk tujuan ini. Hasil shared secret biasanya diproses lebih lanjut menggunakan key derivation function (KDF) sebelum digunakan sebagai kunci enkripsi.

Catatan konseptual

Asymmetric cryptography tidak selalu berarti “mengenkripsi dengan public key”. Dalam protokol modern, fungsi kunci publik dapat berupa autentikasi tanda tangan atau key agreement. Pada TLS 1.3, pertukaran kunci umumnya menggunakan (EC)DHE atau mekanisme PSK; RSA tidak digunakan sebagai static RSA key transport seperti pada beberapa konfigurasi TLS lama.

Kriptografi kunci publik mempermudah distribusi public key dan mendukung autentikasi berbasis pasangan kunci. Namun, operasi kunci publik umumnya lebih berat dan membutuhkan mekanisme untuk memastikan bahwa public key benar-benar milik pihak yang diklaim. Di sinilah sertifikat digital dan PKI menjadi penting.

2.3 Cryptographic Hash Function

Cryptographic hash function adalah fungsi yang menerima input dengan panjang bervariasi dan menghasilkan keluaran berukuran tetap yang disebut hash, digest, atau message digest. Contoh yang umum digunakan adalah SHA-256, yang menghasilkan digest sepanjang 256 bit atau 32 byte. Jika ditampilkan dalam hexadecimal, hasilnya terdiri atas 64 karakter.

Hash function bersifat deterministik: input yang sama akan menghasilkan hash yang sama. Perubahan sekecil apa pun pada input diharapkan menghasilkan keluaran yang berbeda secara signifikan. Sifat ini dikenal sebagai avalanche effect. Hash kriptografis yang baik juga dirancang agar sulit mencari input yang menghasilkan digest tertentu atau menemukan dua input berbeda dengan digest yang sama.

Sifat Keamanan Hash

  • Preimage resistance: ketika digest diketahui, sulit menemukan input yang menghasilkan digest tersebut.
  • Second-preimage resistance: ketika satu input diketahui, sulit menemukan input berbeda dengan digest yang sama.
  • Collision resistance: sulit menemukan dua input berbeda yang menghasilkan digest sama.

SHA-256 dan SHA-3

SHA-256 merupakan anggota keluarga SHA-2 dan menghasilkan digest 256 bit. SHA-3 merupakan keluarga standar hash yang menggunakan konstruksi berbeda, yaitu sponge construction. SHA-256 dan SHA3-256 sama-sama menghasilkan digest 256 bit, tetapi keduanya tidak menghasilkan nilai yang sama untuk input yang sama karena algoritmanya berbeda.

Hash untuk Verifikasi Integritas File

Organisasi dapat menghitung hash file sumber, kemudian memublikasikan atau mengirimkan digest melalui saluran yang dipercaya. Penerima menghitung hash file yang diterima dan membandingkannya dengan digest acuan. Jika nilainya sama, hal itu memberikan bukti kuat bahwa file yang diperiksa sama dengan file yang menjadi acuan, dengan asumsi fungsi hash aman dan digest acuan tidak dimanipulasi.

Batasan hash biasa

Jika penyerang dapat mengubah file sekaligus mengganti digest acuan, perbandingan hash saja tidak membuktikan keaslian sumber. Untuk autentikasi, gunakan HMAC, digital signature, atau distribusikan digest melalui kanal tepercaya.

Hash dan Password

Hash umum seperti SHA-256 tidak ideal digunakan sendirian untuk menyimpan password. Password biasanya memiliki entropi rendah dan dapat ditebak melalui brute force atau dictionary attack. Penyimpanan password sebaiknya menggunakan password hashing/KDF khusus seperti Argon2id, scrypt, bcrypt, atau PBKDF2 dengan salt unik dan parameter biaya yang sesuai. Ini berbeda dari hash cepat yang digunakan untuk memeriksa integritas file.

2.4 Message Authentication Code (MAC)

Message Authentication Code (MAC) adalah nilai autentikasi yang dihitung berdasarkan pesan dan secret key yang diketahui oleh pihak-pihak yang berkomunikasi. Penerima menghitung ulang MAC dari pesan yang diterima menggunakan secret yang sama. Jika hasilnya sesuai, penerima memperoleh bukti bahwa pesan tidak berubah sejak dibuat oleh pihak yang memiliki secret tersebut.

HMAC (Keyed-Hash Message Authentication Code) adalah konstruksi MAC yang menggunakan fungsi hash kriptografis, misalnya HMAC-SHA-256. HMAC menggabungkan secret key dan hash function dengan konstruksi yang dirancang untuk autentikasi pesan. HMAC bukan sekadar menambahkan password ke depan pesan lalu melakukan hash.

Digital Signature and Authentication

Memahami tanda tangan digital sebagai mekanisme untuk memverifikasi integritas pesan dan keterkaitannya dengan pemilik private key.

3.1 Konsep Digital Signature

Digital signature atau tanda tangan digital adalah mekanisme kriptografi yang memungkinkan penerima memeriksa apakah suatu pesan atau dokumen ditandatangani menggunakan private key yang berpasangan dengan public key verifikasi. Tanda tangan digital bukan gambar tanda tangan yang ditempelkan pada dokumen, melainkan nilai kriptografis yang terikat pada data yang ditandatangani.

Digital signature digunakan untuk dokumen elektronik, distribusi software, pembaruan sistem, sertifikat digital, dan transaksi digital. Pada distribusi software, misalnya, pengguna dapat memeriksa signature untuk memastikan paket berasal dari penerbit yang memiliki kunci penandatangan yang dipercaya dan tidak berubah sejak ditandatangani.

3.2 Mekanisme Digital Signature

Proses tanda tangan digital melibatkan dua tahap utama: signing oleh pengirim dan verification oleh penerima. Dalam banyak skema, fungsi hash digunakan sebagai bagian dari proses signature agar pesan berukuran besar dapat diproses secara efisien.

  1. Menyiapkan pesan: pengirim membuat dokumen atau pesan yang akan ditandatangani.
  2. Menghitung representasi pesan: skema signature memproses pesan, biasanya melalui hash yang ditentukan algoritma.
  3. Signing: private key penandatangan digunakan untuk menghasilkan signature sesuai skema.
  4. Mengirimkan data: pesan dan signature dikirim kepada penerima; public key atau sertifikat yang relevan tersedia untuk verifikasi.
  5. Verification: penerima menggunakan public key untuk memverifikasi signature terhadap pesan.
  6. Menafsirkan hasil: verifikasi valid berarti signature cocok dengan pesan dan public key tersebut; verifikasi tidak valid berarti ada ketidaksesuaian atau masalah lain yang perlu ditelusuri.

Jika isi pesan berubah setelah ditandatangani, proses verifikasi seharusnya gagal. Hal yang sama berlaku apabila signature diubah atau public key yang digunakan tidak sesuai. Digital signature membantu menjaga integritas dan autentikasi sumber berdasarkan kepercayaan terhadap public key.

3.3 Karakteristik Digital Signature

  • Authenticity: signature valid menunjukkan signature dibuat dengan private key yang cocok dengan public key verifikasi. Identitas pemilik public key tetap perlu dibuktikan, misalnya melalui sertifikat valid.
  • Integrity: signature terikat pada data yang ditandatangani. Perubahan data menyebabkan verifikasi gagal.
  • Non-repudiation: signature dapat mendukung pembuktian tindakan penandatanganan. Kekuatan pembuktiannya bergantung pada pengamanan private key, proses identifikasi, waktu, kebijakan, dan bukti pendukung.
Signature valid bukan berarti konten pasti benar

Dokumen berbahaya atau informasi yang salah tetap dapat ditandatangani secara valid. Digital signature membuktikan kesesuaian kriptografis antara pesan, signature, dan public key; bukan menilai kebenaran isi atau keamanan dokumen.

3.4 Algoritma Digital Signature

  • RSA-based signature: menggunakan pasangan kunci RSA dan skema signature yang sesuai, misalnya RSASSA-PSS. RSA untuk signature berbeda dari RSA-OAEP yang digunakan untuk enkripsi.
  • ECDSA (Elliptic Curve Digital Signature Algorithm): algoritma signature berbasis kurva eliptik. Keamanan dan keabsahannya sangat bergantung pada parameter serta penggunaan nonce penandatanganan yang benar.
  • EdDSA (Edwards-Curve Digital Signature Algorithm): keluarga algoritma signature yang mencakup Ed25519 dan dirancang untuk implementasi efisien dengan karakteristik tertentu.

Implementasi sebaiknya menggunakan pustaka kriptografi yang terpelihara dan konfigurasi standar. Membuat algoritma signature sendiri atau mengubah prosedur matematis tanpa analisis ahli dapat menghasilkan sistem yang tidak aman.

  6. Catat hasil verifikasi yang menunjukkan signature valid.

  3. Jalankan Verify kembali.
  4. Catat bahwa verifikasi seharusnya gagal karena pesan tidak lagi sama dengan pesan yang ditandatangani.

Cryptographic Key Management

Memahami bahwa keamanan algoritma bergantung pada proses pembuatan, distribusi, penyimpanan, penggunaan, pergantian, dan penghancuran kunci.

4.1 Konsep Cryptographic Key Management

Cryptographic key management adalah pengelolaan kunci kriptografi sepanjang masa penggunaannya. Kunci merupakan komponen sensitif karena penguasaan kunci dapat memberikan kemampuan membaca data terenkripsi, membuat MAC, atau menandatangani pesan, sesuai jenis kuncinya.

Pengelolaan kunci yang baik mencakup kebijakan siapa yang boleh membuat dan menggunakan kunci, di mana kunci disimpan, bagaimana kunci didistribusikan, kapan kunci harus diganti, bagaimana pencabutan dilakukan, serta bagaimana kunci dihancurkan ketika tidak lagi diperlukan.

Tidak semua jenis kunci mengikuti siklus yang sama; kebijakan harus mempertimbangkan tujuan, masa berlaku, dan risiko masing-masing kunci.

4.2 Key Generation

Key generation adalah proses menghasilkan kunci dengan nilai yang cukup tidak terduga. Kunci yang dibuat dari pola sederhana, angka berurutan, tanggal lahir, atau sumber acak yang lemah dapat ditebak dan melemahkan sistem.

Perangkat lunak kriptografi menggunakan cryptographically secure pseudorandom number generator (CSPRNG) untuk menghasilkan nilai acak yang sesuai kebutuhan keamanan. Kualitas sumber acak berhubungan dengan entropy, yaitu ukuran ketidakpastian yang tersedia pada proses pembentukan nilai.

Panjang kunci harus dipilih berdasarkan algoritma dan rekomendasi standar. Kunci yang lebih panjang tidak otomatis membuat implementasi aman jika generator acaknya lemah, kunci bocor, atau algoritma digunakan dengan cara yang salah.

Key Derivation Function (KDF)

KDF mengubah secret awal menjadi satu atau lebih kunci dengan karakteristik yang dibutuhkan. HKDF, misalnya, digunakan untuk menurunkan kunci dari material secret yang telah tersedia dalam protokol kriptografi. Untuk password manusia yang memiliki entropi rendah, password-based KDF seperti Argon2id, scrypt, atau PBKDF2 digunakan dengan salt dan parameter biaya yang sesuai.

4.3 Key Distribution and Exchange

Distribusi kunci merupakan salah satu tantangan utama symmetric cryptography. Jika secret key dikirim melalui saluran yang dapat diamati tanpa perlindungan, penyerang mungkin memperoleh kunci dan membaca komunikasi. Oleh sebab itu, organisasi dapat menggunakan saluran out-of-band yang aman, sistem manajemen kunci, atau protokol key establishment.

Diffie-Hellman Key Exchange

Diffie-Hellman memungkinkan dua pihak membentuk shared secret melalui jaringan yang dapat diamati. Setiap pihak memiliki nilai privat dan nilai publik yang dihitung dari parameter bersama. Masing-masing pihak menggabungkan nilai privatnya dengan nilai publik pihak lain untuk memperoleh hasil secret yang sama.

Penyerang yang hanya mengamati nilai publik secara umum tidak dapat memperoleh shared secret secara praktis jika parameter dan algoritma dipilih dengan benar. Namun, Diffie-Hellman tanpa autentikasi tidak memastikan identitas lawan komunikasi. Penyerang aktif dapat melakukan Man-in-the-Middle dengan membuat dua pertukaran kunci terpisah.

ECDH dan ECDHE

ECDH merupakan key agreement berbasis kurva eliptik. ECDHE menggunakan pasangan kunci ephemeral atau sementara untuk setiap sesi. Jika diterapkan dengan benar dan kunci sementara tidak disimpan secara tidak semestinya, ECDHE mendukung forward secrecy: kebocoran private key jangka panjang di kemudian hari tidak otomatis membuka sesi lama yang telah direkam.

Perbedaan penting

Key exchange menghasilkan atau membantu membentuk secret bersama. Authentication memverifikasi siapa lawan komunikasi. Protokol aman biasanya menggabungkan keduanya agar shared secret tidak terbentuk dengan pihak yang salah.

4.4 Key Storage and Protection

Kunci harus disimpan dengan perlindungan yang sesuai tingkat sensitivitasnya. Private key server, misalnya, tidak boleh disimpan dalam repositori kode publik atau dibagikan melalui pesan biasa. Secret key aplikasi perlu dibatasi aksesnya dan tidak ditulis langsung di source code.

  • Access control: hanya identitas atau layanan yang berwenang yang boleh menggunakan kunci.
  • Encryption at rest: kunci dapat dilindungi menggunakan mekanisme enkripsi ketika disimpan.
  • Password protection: private key dapat dilindungi dengan passphrase, tetapi passphrase harus dikelola dengan aman.
  • Hardware Security Module (HSM): perangkat khusus yang membantu menghasilkan, menyimpan, dan menggunakan kunci dalam lingkungan terlindungi.
  • Audit logging: aktivitas penggunaan dan perubahan kunci dicatat untuk membantu pemantauan dan investigasi.
  • Backup and recovery: kunci penting dapat memiliki mekanisme pencadangan terkontrol agar layanan dapat dipulihkan.

Backup kunci juga merupakan aset sensitif. Salinan cadangan yang tidak terlindungi dapat menjadi jalur kebocoran. Karena itu, kebijakan penyimpanan, pemulihan, pemisahan tugas, dan penghancuran harus dirancang sejak awal.

4.5 Key Rotation, Revocation, and Destruction

Key rotation adalah pergantian kunci secara terencana atau berdasarkan kondisi tertentu. Tujuannya membatasi dampak jika kunci terpapar, mengurangi masa penggunaan kunci, dan mengikuti kebijakan organisasi. Pergantian kunci perlu disertai proses migrasi agar data atau layanan yang masih bergantung pada kunci lama tetap dapat ditangani secara benar.

Revocation berarti mencabut kepercayaan atau otorisasi penggunaan kunci maupun sertifikat. Dalam PKI, sertifikat dapat dicabut sebelum masa berlakunya berakhir, misalnya karena private key diduga bocor atau informasi identitas tidak lagi valid.

Key destruction adalah penghancuran kunci secara aman ketika tidak lagi dibutuhkan. Penghapusan harus memperhatikan kemungkinan adanya salinan, backup, cache, atau replika. Jika kunci telah dikompromikan, organisasi perlu menghentikan penggunaannya, mencabut sertifikat jika relevan, membuat kunci pengganti, dan menilai data atau layanan yang terdampak.

Bab V

Public Key Infrastructure and Digital Certificates

Memahami bagaimana identitas digital dihubungkan dengan public key dan bagaimana browser atau sistem memeriksa kepercayaan terhadap sertifikat.

5.1 Konsep Public Key Infrastructure (PKI)

Public Key Infrastructure (PKI) merupakan kerangka yang terdiri atas kebijakan, peran, prosedur, perangkat lunak, dan komponen kriptografi untuk menerbitkan, mengelola, memvalidasi, dan mencabut sertifikat digital. PKI membantu menjawab pertanyaan penting: bagaimana penerima mengetahui bahwa public key yang diterimanya benar-benar terkait dengan identitas yang diklaim?

Public key dapat dibagikan secara terbuka, tetapi penerima tetap perlu memastikan pemiliknya. Jika penyerang mengganti public key server dengan public key miliknya, komunikasi dapat diarahkan ke pihak yang salah. Sertifikat digital yang ditandatangani CA membantu mengikat identitas server dengan public key tertentu.

5.2 Komponen PKI

  • Certificate Authority (CA): entitas yang menerbitkan dan menandatangani sertifikat setelah proses validasi sesuai kebijakan.
  • Registration Authority (RA): pihak atau fungsi yang membantu memverifikasi identitas pemohon sebelum sertifikat diterbitkan.
  • Digital Certificate: dokumen digital yang memuat identitas, public key, masa berlaku, dan tanda tangan penerbit.
  • Certificate Repository: lokasi penyimpanan atau distribusi sertifikat dan informasi terkait.
  • Certificate Revocation List (CRL): daftar sertifikat yang telah dicabut oleh CA.
  • Trust Anchor / Root CA: akar kepercayaan yang telah dipasang atau dipercaya oleh sistem.
  • Intermediate CA: CA perantara yang menerbitkan sertifikat lanjutan dan membangun rantai kepercayaan menuju root.

5.4 Certificate Validation

Validasi sertifikat dilakukan untuk menentukan apakah sertifikat dapat dipercaya untuk identitas dan tujuan tertentu. Pemeriksaan ini bukan sekadar melihat apakah sertifikat masih berlaku. Beberapa aspek perlu diperiksa secara bersamaan.

  1. Domain / Service Identity: nama host yang diakses harus cocok dengan identitas yang tercantum pada sertifikat, umumnya melalui SAN.
  2. Validity Period: waktu sistem harus berada dalam periode berlaku sertifikat.
  3. Signature Validation: tanda tangan sertifikat harus valid terhadap public key penerbit.
  4. Chain of Trust: rantai sertifikat harus dapat dibangun menuju trust anchor yang dipercaya.
  5. Key Usage: penggunaan sertifikat harus sesuai tujuan yang diizinkan.
  6. Revocation Status: status pencabutan dapat diperiksa melalui CRL atau OCSP sesuai kebijakan dan dukungan sistem.

OCSP (Online Certificate Status Protocol) menyediakan cara untuk meminta informasi status sertifikat dari responder. Dalam beberapa konfigurasi, server dapat mengirimkan respons OCSP yang telah ditandatangani melalui mekanisme OCSP stapling. Pemeriksaan pencabutan di browser dapat memiliki kebijakan dan perilaku berbeda, sehingga tidak tepat menganggap semua browser selalu melakukan pemeriksaan online dengan cara yang sama.

Makna ikon gembok

Ikon gembok atau indikator HTTPS menunjukkan bahwa browser berhasil membangun koneksi yang memenuhi pemeriksaan teknis tertentu. Hal tersebut tidak membuktikan bahwa isi website benar, penjual dapat dipercaya, atau layanan bebas penipuan.

5.5 Peran PKI dalam Autentikasi

Dalam koneksi HTTPS, server mengirimkan sertifikat sebagai bagian dari proses TLS ketika autentikasi berbasis sertifikat digunakan. Browser memeriksa sertifikat dan memastikan identitas server sesuai dengan domain yang diminta. Dengan demikian, sertifikat membantu mencegah penyamaran server selama validasi dilakukan dengan benar.

Kepercayaan pada sertifikat bergantung pada trust store perangkat atau browser, kebijakan CA, masa berlaku, validitas rantai, dan kecocokan identitas layanan. Jika pengguna mengabaikan peringatan sertifikat atau memasang root CA yang tidak tepercaya, perlindungan autentikasi dapat melemah.

Bab VI

Secure Communication Protocols

Mempelajari protokol yang menerapkan kriptografi untuk membangun saluran komunikasi aman, terutama HTTPS/TLS, SSH, dan VPN.

6.1 Konsep Secure Communication

Secure communication adalah komunikasi yang menggunakan mekanisme teknis dan prosedural untuk melindungi data dari pembacaan, perubahan, pemalsuan, atau penyamaran pihak. Dalam jaringan, data melewati berbagai perangkat dan media transmisi. Tidak semua bagian jalur tersebut berada di bawah kendali pengirim dan penerima.

Protokol komunikasi aman mengatur bagaimana pihak-pihak mengenali satu sama lain, menyepakati parameter kriptografi, membentuk kunci, melindungi pesan, serta menangani kegagalan autentikasi atau integritas. Dengan demikian, secure communication bukan hanya penggunaan satu algoritma, melainkan kombinasi beberapa mekanisme yang saling mendukung.

6.2 HTTP dan HTTPS

HTTP (Hypertext Transfer Protocol) merupakan protokol lapisan aplikasi untuk pertukaran pesan web antara client dan server. HTTP sendiri tidak menyediakan enkripsi transport. Jika digunakan tanpa lapisan perlindungan tambahan, isi request dan response dapat diamati atau dimodifikasi oleh pihak yang memiliki akses pada jalur komunikasi.

HTTPS (HTTP Secure) adalah HTTP yang dijalankan melalui koneksi TLS. TLS memberikan perlindungan kriptografis terhadap data aplikasi selama transmisi, serta autentikasi server pada pola penggunaan web yang umum.

6.3 Secure Sockets Layer (SSL) dan Transport Layer Security (TLS)

SSL (Secure Sockets Layer) merupakan pendahulu TLS. Karena kelemahan keamanan yang ditemukan, SSL versi lama tidak layak digunakan pada konfigurasi modern. TLS dikembangkan sebagai penerus SSL dan menjadi protokol standar untuk membangun saluran komunikasi client-server yang aman.

TLS menyediakan tiga properti utama pada saluran yang telah terbentuk: autentikasi server (autentikasi klien bersifat opsional), confidentiality, dan integrity. TLS tidak menjamin keamanan endpoint. Jika perangkat client atau server telah terinfeksi malware, penyerang mungkin dapat membaca data sebelum dienkripsi atau setelah didekripsi.

TLS 1.2 dan TLS 1.3

TLS 1.2 masih ditemukan pada berbagai sistem yang harus menjaga kompatibilitas. TLS 1.3 menyederhanakan dan memperkuat sejumlah aspek protokol, termasuk menghapus banyak algoritma lama, menggunakan authenticated encryption untuk perlindungan record, memperbaiki proses key derivation, dan mengurangi jumlah perjalanan pesan pada handshake.

6.4 TLS Handshake Protocol

TLS handshake merupakan proses awal yang memungkinkan client dan server menyepakati parameter keamanan, mengautentikasi pihak, dan membentuk material kunci. Setelah proses ini selesai, data aplikasi dapat dilindungi menggunakan kunci trafik.

Gambaran konseptual TLS 1.3 untuk pola autentikasi sertifikat server. Detail pesan dapat berbeda pada PSK, resumption, client authentication, dan kondisi HelloRetryRequest.

Penjelasan pesan utama:

  • ClientHello: client mengirim versi yang didukung, cipher suites, extensions, dan biasanya key share. Informasi seperti Server Name Indication (SNI) dan Application-Layer Protocol Negotiation (ALPN) dapat dibawa melalui extension.
  • ServerHello: server memilih parameter yang sesuai dan mengirim key share. Kedua pihak dapat mulai menurunkan handshake secrets.
  • EncryptedExtensions: server menyampaikan extension yang dipilih dan dilindungi setelah kunci handshake tersedia.
  • Certificate: server mengirim rantai sertifikat pada pola autentikasi berbasis sertifikat.
  • CertificateVerify: server membuktikan kepemilikan private key dengan menandatangani transcript handshake.
  • Finished: pesan ini memberikan verifikasi kriptografis atas transcript handshake dan mengonfirmasi bahwa pihak memiliki kunci handshake yang benar.
  • Application Data: data aplikasi dilindungi menggunakan traffic keys dan mekanisme AEAD.

Certificate dan CertificateVerify tidak selalu muncul pada semua pola TLS 1.3. Misalnya, penggunaan Pre-Shared Key (PSK) untuk session resumption dapat memiliki alur berbeda. Pada mutual TLS, server juga dapat meminta sertifikat client.

Cipher Suite pada TLS 1.3

Dalam TLS 1.3, nama cipher suite terutama menentukan algoritma AEAD dan hash yang digunakan dalam key schedule. Mekanisme key exchange dan signature dinegosiasikan melalui parameter atau extension terpisah. Hal ini berbeda dari cara beberapa cipher suite TLS 1.2 menggabungkan lebih banyak komponen dalam satu nama suite.

0-RTT dan Risiko Replay

TLS 1.3 dapat mendukung early data 0-RTT pada session resumption. Fitur ini mengurangi waktu tunggu, tetapi data early data dapat memiliki risiko replay. Aplikasi perlu membatasi operasi yang dikirim melalui 0-RTT, khususnya operasi yang mengubah keadaan seperti pembayaran atau pengiriman pesanan, kecuali tersedia perlindungan replay yang sesuai.

6.5 TLS Record Protocol

Setelah handshake membentuk kunci trafik, TLS menggunakan record protocol untuk membawa data aplikasi. Data dibagi menjadi unit-unit record, kemudian dilindungi menggunakan algoritma AEAD yang disepakati. AEAD menyediakan enkripsi sekaligus autentikasi integritas record, sehingga perubahan data dapat dideteksi.

Pada sisi penerima, record diverifikasi terlebih dahulu. Jika autentikasi gagal, data tidak boleh diteruskan sebagai data aplikasi yang sah. Dengan demikian, TLS melindungi data yang melintasi jaringan dari pembacaan dan manipulasi yang tidak terdeteksi, selama implementasi dan endpoint tidak dikompromikan.

6.6 Secure Shell (SSH)

Secure Shell (SSH) adalah protokol untuk akses jarak jauh dan komunikasi aman antara client dan server. SSH umum digunakan administrator untuk mengelola server Linux/Unix, menjalankan perintah, memindahkan file melalui SCP/SFTP, atau membuat port forwarding.

SSH membangun koneksi melalui beberapa tahap: negosiasi algoritma, key exchange, autentikasi host server, pembentukan saluran terenkripsi, lalu autentikasi pengguna. Dengan demikian, SSH tidak hanya mengenkripsi terminal, tetapi juga perlu memastikan bahwa pengguna terhubung ke host yang benar.

Autentikasi pada SSH

  • Password-based authentication: pengguna membuktikan identitas dengan password. Keamanannya bergantung pada kekuatan password, pembatasan percobaan, dan konfigurasi server.
  • Public key authentication: pengguna memiliki pasangan kunci. Public key ditempatkan pada akun server, sedangkan private key tetap disimpan dan dilindungi pada perangkat pengguna.
  • Host authentication: client memeriksa host key server. Fingerprint host perlu diverifikasi melalui sumber tepercaya ketika pertama kali terhubung.

File known_hosts pada OpenSSH dapat menyimpan identitas host yang pernah diverifikasi. Jika fingerprint berubah secara tidak terduga, pengguna tidak boleh langsung mengabaikan peringatan. Perubahan dapat disebabkan penggantian server yang sah, tetapi juga dapat menunjukkan risiko penyamaran.

Perbedaan autentikasi user dan host

Autentikasi user menjawab “siapa pengguna yang masuk ke server?”. Autentikasi host menjawab “apakah server yang dihubungi benar-benar server yang dimaksud?”. Keduanya penting untuk remote administration yang aman.

6.7 Virtual Private Network (VPN)

Virtual Private Network (VPN) membangun koneksi logis atau tunnel melalui jaringan perantara sehingga lalu lintas antara endpoint dapat dilindungi. VPN sering digunakan untuk menghubungkan pengguna jarak jauh ke jaringan organisasi atau menghubungkan dua jaringan kantor melalui internet.

Tunneling dan Encryption

Tunneling membungkus paket atau lalu lintas jaringan agar dapat dibawa melalui jaringan lain. Enkripsi dan autentikasi dapat diterapkan pada tunnel untuk melindungi data dari pengamatan dan perubahan. VPN bukan satu algoritma tunggal; keamanan VPN bergantung pada protokol, algoritma, autentikasi, konfigurasi, dan pengelolaan kunci.

IPsec

Internet Protocol Security (IPsec) adalah kumpulan protokol untuk melindungi komunikasi pada lapisan IP. IPsec mencakup mekanisme seperti Encapsulating Security Payload (ESP), yang dapat memberikan confidentiality, integrity, dan autentikasi asal data sesuai konfigurasi. Internet Key Exchange (IKE), umumnya IKEv2, digunakan untuk menegosiasikan Security Associations dan material kunci.

Jenis VPN

  • Remote access VPN: menghubungkan perangkat individu, seperti laptop pegawai, ke jaringan organisasi.
  • Site-to-site VPN: menghubungkan jaringan pada lokasi berbeda, misalnya kantor pusat dan kantor cabang.
  • Transport mode IPsec: melindungi payload paket IP, umumnya untuk komunikasi host-to-host.
  • Tunnel mode IPsec: membungkus seluruh paket IP asli ke dalam paket IP baru, umum digunakan untuk gateway-to-gateway VPN.

VPN berbeda dari TLS. VPN umumnya melindungi lalu lintas pada tingkat jaringan atau tunnel, sedangkan TLS melindungi koneksi aplikasi yang menggunakan TLS. VPN juga tidak otomatis membuat pengguna anonim atau melindungi perangkat dari malware. Penyedia atau gateway VPN dapat melihat lalu lintas setelah keluar dari tunnel, kecuali lalu lintas tersebut dilindungi lagi oleh protokol end-to-end seperti HTTPS.

Data in Transit Security and Network Protection

Mengidentifikasi ancaman terhadap komunikasi jaringan dan memahami bagaimana mekanisme kriptografi melindungi data selama transmisi.

7.1 Konsep Data in Transit

Data in transit adalah data yang sedang berpindah dari satu perangkat atau sistem ke perangkat atau sistem lain melalui media komunikasi. Contohnya adalah kredensial yang dikirim browser ke server, data pembayaran yang dikirim aplikasi ke gateway, atau file yang dipindahkan melalui jaringan.

Keamanan informasi sering dibahas melalui tiga keadaan data:

Data at rest

Data yang sedang tersimpan, misalnya dokumen pada SSD atau database.

Data in use

Data yang sedang diproses, misalnya isi file dalam memori aplikasi.

Data in transit

Data yang sedang dikirim melalui jaringan, misalnya request HTTPS.

Setiap keadaan data memiliki risiko dan kontrol yang berbeda. Enkripsi disk membantu melindungi data at rest, kontrol akses dan keamanan proses membantu melindungi data in use, sedangkan TLS, SSH, atau VPN dapat melindungi data in transit.

7.2 Ancaman terhadap Komunikasi Data

Eavesdropping

Eavesdropping adalah tindakan mengamati atau menyadap komunikasi tanpa izin. Jika data dikirim tanpa enkripsi, informasi sensitif seperti kredensial atau isi pesan dapat terbaca oleh pihak yang memiliki akses ke jalur komunikasi.

Packet Sniffing

Packet sniffing adalah proses menangkap paket jaringan untuk dianalisis. Teknik ini digunakan secara sah oleh administrator untuk troubleshooting, audit, dan pembelajaran. Namun, penyerang dapat menyalahgunakannya untuk mengumpulkan informasi. Jika protokol telah menggunakan TLS dengan benar, payload aplikasi umumnya tidak dapat dibaca hanya dari packet capture, walaupun metadata tertentu tetap terlihat.

Man-in-the-Middle (MITM)

MITM terjadi ketika penyerang menempatkan dirinya di antara dua pihak dan berusaha mengamati, meneruskan, atau memodifikasi komunikasi. Serangan dapat berhasil jika autentikasi endpoint tidak dilakukan dengan benar, sertifikat tidak divalidasi, atau pengguna mengabaikan peringatan keamanan.

Data Tampering

Data tampering merupakan perubahan isi pesan atau paket selama transmisi. Tanpa perlindungan integritas, penerima mungkin tidak mengetahui bahwa data telah diubah. MAC, digital signature, dan AEAD dapat membantu mendeteksi perubahan sesuai konteks penggunaannya.

Replay Attack

Replay attack terjadi ketika penyerang menangkap pesan atau bukti autentikasi yang sah lalu mengirimkannya kembali untuk mengulangi tindakan. Nonce, timestamp, sequence number, challenge-response, dan mekanisme anti-replay dapat digunakan sesuai protokol.

Session Hijacking

Session hijacking adalah pengambilalihan sesi yang telah terautentikasi, misalnya melalui pencurian session cookie atau token. TLS melindungi token saat transit, tetapi tidak mencegah pencurian token dari endpoint yang telah terkompromi. Aplikasi juga perlu mengatur cookie Secure, HttpOnly, SameSite, masa berlaku sesi, dan mekanisme logout.

Downgrade Attack

Downgrade attack mencoba memaksa client dan server menggunakan versi protokol atau parameter keamanan yang lebih lemah. Perlindungan mencakup konfigurasi versi yang aman, mekanisme downgrade protection, dan penolakan terhadap protokol atau cipher suite usang.

Traffic Analysis

Traffic analysis mempelajari pola komunikasi seperti waktu, frekuensi, ukuran paket, dan hubungan antarendpoint. Enkripsi payload tidak selalu menyembunyikan metadata tersebut. Pada beberapa sistem, padding atau mekanisme tambahan dapat mengurangi informasi yang bocor melalui pola trafik.

7.3 Mekanisme Perlindungan Data dalam Transit

Perlindungan data dalam transit harus disusun sebagai kombinasi kontrol. Enkripsi melindungi isi data, tetapi perlu autentikasi untuk memastikan pihak yang berkomunikasi benar. Integritas diperlukan agar perubahan dapat dideteksi, sedangkan key exchange dan key management memastikan kunci dibentuk dan digunakan dengan aman.

  • Encryption in transit: melindungi isi komunikasi dari pembacaan pihak yang tidak berwenang.
  • Message integrity: memastikan perubahan pada data dapat dideteksi.
  • Server authentication: memverifikasi identitas server sebelum data sensitif dikirimkan.
  • Mutual authentication: kedua endpoint saling mengautentikasi ketika model sistem membutuhkannya, misalnya mutual TLS.
  • Secure key exchange: membentuk material kunci tanpa mengirim secret secara terbuka.
  • Certificate validation: memeriksa apakah identitas dan rantai sertifikat dapat dipercaya.

7.4 Perlindungan Komunikasi Menggunakan TLS

Ketika browser mengakses website HTTPS, browser dan server membangun koneksi TLS. Client memulai handshake, server merespons dengan parameter yang dipilih, dan kedua pihak menjalankan proses autentikasi serta pembentukan kunci. Setelah handshake berhasil, data HTTP dilindungi oleh TLS record protocol.

Jika seorang pengamat menangkap paket TLS, ia mungkin dapat mengidentifikasi alamat IP, port, waktu komunikasi, ukuran paket, dan sebagian informasi awal koneksi. Namun, payload aplikasi yang dilindungi TLS tidak dapat dibaca secara langsung tanpa kunci atau akses ke endpoint. Inilah perbedaan antara melihat paket dan memahami isi aplikasi di dalam paket.

TLS tidak melindungi data sebelum masuk ke proses enkripsi atau setelah keluar dari proses dekripsi. Oleh karena itu, keamanan endpoint, browser, server, aplikasi, dan pengelolaan sesi tetap diperlukan.

7.5 Evaluasi Keamanan Komunikasi

Evaluasi komunikasi aman bertujuan memeriksa apakah protokol dan konfigurasi yang digunakan memberikan perlindungan sesuai kebutuhan. Evaluasi dapat dilakukan melalui pemeriksaan sertifikat, konfigurasi TLS, dan analisis packet capture.

  • Identifikasi protokol: menentukan apakah komunikasi menggunakan HTTP, HTTPS, SSH, atau protokol lain.
  • Versi TLS: memeriksa versi protokol yang didukung dan dinegosiasikan.
  • Cipher suites: memeriksa algoritma AEAD dan parameter kriptografi yang dipilih.
  • Sertifikat: memeriksa subject/SAN, issuer, masa berlaku, signature, dan chain of trust.
  • Packet capture: mengenali alur TCP, ClientHello, ServerHello, dan Application Data.
  • Visibilitas data: membedakan metadata yang terlihat dari payload yang terenkripsi.
  • Kesimpulan evaluasi: menilai apakah confidentiality, integrity, dan authentication diterapkan secara memadai.
Prinsip interpretasi packet capture

Jika Wireshark menampilkan paket TLS Application Data, hal tersebut tidak berarti isi aplikasi dapat dibaca. Label tersebut menunjukkan bahwa data aplikasi dibawa melalui TLS dan dilindungi pada level record. Tanpa kunci sesi, isi payload umumnya tidak dapat ditampilkan sebagai plaintext.

Bab VIII

Cryptographic Security Implementation and Best Practices

Menerapkan prinsip pemilihan algoritma, pengelolaan kunci, validasi sertifikat, dan konfigurasi protokol secara tepat.

8.1 Pemilihan Mekanisme Kriptografi

Pemilihan mekanisme kriptografi harus dimulai dengan mengidentifikasi aset, ancaman, kebutuhan keamanan, dan pihak yang harus dipercaya. Tidak ada satu algoritma yang dapat memenuhi seluruh kebutuhan. Sistem biasanya menggabungkan beberapa mekanisme.

8.2 Cryptographic Best Practices

  • Gunakan algoritma standar: pilih algoritma dan parameter yang direkomendasikan standar relevan. Hindari cipher buatan sendiri.
  • Gunakan authenticated encryption: untuk enkripsi aplikasi, pertimbangkan mode AEAD seperti AES-GCM atau algoritma AEAD lain yang sesuai.
  • Kelola nonce/IV dengan benar: ikuti persyaratan unik atau acak sesuai mode. Jangan menggunakan ulang nonce AES-GCM dengan kunci yang sama.
  • Lindungi private key dan secret: batasi akses, gunakan secret manager atau HSM jika sesuai, dan jangan menyimpan kunci di repositori kode.
  • Gunakan random generator yang aman: kunci dan nonce yang memerlukan randomness harus dibuat dengan CSPRNG.
  • Validasi sertifikat: jangan menonaktifkan pemeriksaan hostname atau certificate chain untuk mengatasi error koneksi.
  • Nonaktifkan protokol lemah: hindari SSL dan versi TLS yang sudah tidak direkomendasikan.
  • Lakukan key rotation: buat kebijakan pergantian kunci dan prosedur tanggap insiden saat kunci terkompromi.
  • Terapkan cryptographic agility: rancang sistem agar algoritma dan parameter dapat diperbarui ketika standar atau ancaman berubah.
  • Perbarui perangkat lunak: gunakan pustaka dan sistem yang mendapat pembaruan keamanan.

8.4 Penerapan Kriptografi dalam Sistem Informasi

Transaksi Perbankan Digital

Aplikasi perbankan menggunakan HTTPS/TLS untuk melindungi komunikasi antara aplikasi dan server. Sertifikat membantu aplikasi memverifikasi server, sementara mekanisme autentikasi pengguna dan kontrol transaksi memastikan permintaan berasal dari pengguna yang telah terautentikasi. Perlindungan tambahan seperti token, tanda tangan transaksi, dan pemantauan fraud dapat diterapkan sesuai arsitektur layanan.

E-commerce dan Pembayaran Elektronik

Dalam e-commerce, TLS melindungi data yang dikirim antara browser, platform, dan layanan pembayaran. Integritas request dan autentikasi antarlayanan dapat menggunakan token, MAC, atau sertifikat klien sesuai kebutuhan. Data pembayaran tetap harus ditangani sesuai standar dan kebijakan keamanan yang berlaku.

Komunikasi Email

TLS dapat melindungi koneksi antara mail client dan mail server atau antar mail server pada jalur transport. Namun, TLS transport tidak selalu memberikan enkripsi end-to-end pada isi email. S/MIME atau OpenPGP dapat digunakan untuk menandatangani dan/atau mengenkripsi pesan sehingga perlindungan dapat melekat pada pesan itu sendiri sesuai konfigurasi.

Remote Server Administration

Administrator menggunakan SSH untuk mengakses server dari jarak jauh. SSH menyediakan enkripsi saluran, integritas, autentikasi host, dan autentikasi pengguna. Penggunaan public key authentication, passphrase pada private key, pembatasan hak akses, dan pemeriksaan fingerprint host merupakan praktik penting.

Aplikasi Web dan API

Aplikasi web menggunakan HTTPS untuk melindungi komunikasi browser dan server. API antarlayanan dapat menggunakan TLS, mutual TLS, token akses, atau HMAC sesuai kebutuhan. Secret API harus disimpan di tempat terlindungi, memiliki masa berlaku atau mekanisme rotasi, dan tidak dicatat ke log secara terbuka.

Pertukaran Data Antarserver

Komunikasi antarserver dapat menggunakan TLS untuk autentikasi dan perlindungan koneksi. Mutual TLS dapat digunakan ketika kedua layanan perlu membuktikan identitasnya dengan sertifikat. Pengelolaan sertifikat, rotasi kunci, pemantauan masa berlaku, dan pembaruan konfigurasi harus menjadi bagian dari operasional sistem.

2. Hubungan antara kriptografi dan protokol komunikasi

Protokol komunikasi aman menggabungkan beberapa mekanisme kriptografi yang mempunyai fungsi berbeda. HTTPS menjadi contoh yang mudah ditemui dalam kehidupan sehari-hari.

Certificate / PKI

Mengikat identitas server dengan public key.

Key Exchange

Membentuk shared keying material.

Key Derivation

Menurunkan traffic keys.

AEAD

Melindungi data aplikasi.

Dalam TLS, sertifikat dan bukti kriptografi membantu autentikasi server; key exchange membantu kedua pihak memperoleh material kunci bersama; key derivation menghasilkan kunci trafik; kemudian AEAD melindungi data aplikasi. Setiap tahap memiliki fungsi dan persyaratan keamanan tersendiri.
